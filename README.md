## Расписание и запись на приём

В системе OR используются два независимых сценария записи. Они предназначены для разных задач и не заменяют друг друга.

### 1. Общая запись по вопросам — `booking`

Модуль `booking` предназначен для студентов, которым нужно обратиться по учебному или административному вопросу.

- Рабочие дни: понедельник–пятница.
- Время работы: с 10:00 до 17:00.
- Доступные интервалы формируются с шагом 5 минут.
- Допустимая продолжительность приёма зависит от уровня вопроса.
- Занятые активными записями интервалы недоступны для повторного бронирования.

Источник правил доступности: `booking/slots.py`.

Основные API-адреса:
- `GET /api/booking/route/` — определение маршрута обращения.
- `GET /api/booking/slots/` — доступные интервалы.
- `POST /api/booking/` — создание записи.
- `GET /api/booking/ticket/<code>/` — получение талона.
- `POST /api/booking/<id>/cancel/` — отмена записи.

### 2. Индивидуальная запись к сотруднику — `calendar_for_admin`

Модуль `calendar_for_admin` предназначен для записи посетителя на приём к конкретному администратору по его индивидуальному расписанию.

- Администратор настраивает дни и время приёма.
- Для каждого правила задаётся продолжительность интервала.
- Доступность зависит от действующих правил расписания и уже созданных записей.
- Пересекающиеся активные записи не допускаются.

Источник правил доступности: модели и логика приложения `calendar_for_admin`.

Основные API-адреса:
- `GET /api/calendar/availability/` — доступность для записи.
- `POST /api/calendar/book/` — создание записи.
- `GET /api/calendar/rules/` — правила расписания.
- `GET /api/calendar/appointments/` — записи на приём.

### Какой модуль использовать?

| Сценарий | Модуль |
|---|---|
| Студент выбирает время для обращения по вопросу | `booking` |
| Посетитель выбирает время по индивидуальному графику сотрудника | `calendar_for_admin` |

**Важно:** расписания этих модулей не объединяются автоматически. Изменение индивидуального графика администратора не изменяет фиксированные часы в `booking/slots.py`. Если в будущем потребуется единое расписание, его интеграцию необходимо спроектировать отдельно.

## Запуск без Docker (локально)

Docker не обязателен для разработки, проект можно запустить локально через виртуальное окружение (Windows, PowerShell).

1. Создать и активировать виртуальное окружение:

```powershell
python -m venv venv
.\venv\Scripts\Activate
```

2. Установить зависимости:

```powershell
pip install -r requirements.txt
```

3. Создать файл настроек из примера:

```powershell
copy .env.example .env
```

4. Применить миграции и запустить сервер:

```powershell
python manage.py migrate
python manage.py runserver
```

Сервер будет доступен по адресу http://127.0.0.1:8000/.

**Примечание:** если в `.env` настроена база PostgreSQL из `docker-compose.yml`, для локального запуска без Docker нужно указать доступную базу данных.
