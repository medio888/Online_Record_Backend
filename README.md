## Расписание и запись на приём

В системе OR используются два независимых сценария записи. Они предназначены для разных задач и не заменяют друг друга.

### 1. Общая запись по вопросам — `booking`

Модуль `booking` предназначен для студентов, которым нужно обратиться по учебному или административному вопросу.

- Рабочие дни: понедельник–пятница.
- Время работы: с 10:00 до 17:00.
- Доступные интервалы формируются с шагом 5 минут.
- Допустимая продолжительность приёма зависит от уровня вопроса.
- Занятые активными записями интервалы недоступны для повторного бронирования.

Источник правил доступности: `booking/slots.py`.

Основные API-адреса:
- `GET /api/booking/route/` — определение маршрута обращения.
- `GET /api/booking/slots/` — доступные интервалы.
- `POST /api/booking/` — создание записи.
- `GET /api/booking/ticket/<code>/` — получение талона.
- `POST /api/booking/<id>/cancel/` — отмена записи.

### 2. Индивидуальная запись к сотруднику — `calendar_for_admin`

Модуль `calendar_for_admin` предназначен для записи посетителя на приём к конкретному администратору по его индивидуальному расписанию.

- Администратор настраивает дни и время приёма.
- Для каждого правила задаётся продолжительность интервала.
- Доступность зависит от действующих правил расписания и уже созданных записей.
- Пересекающиеся активные записи не допускаются.

Источник правил доступности: модели и логика приложения `calendar_for_admin`.

Основные API-адреса:
- `GET /api/calendar/availability/` — доступность для записи.
- `POST /api/calendar/book/` — создание записи.
- `GET /api/calendar/rules/` — правила расписания.
- `GET /api/calendar/appointments/` — записи на приём.

### Какой модуль использовать?

| Сценарий | Модуль |
|---|---|
| Студент выбирает время для обращения по вопросу | `booking` |
| Посетитель выбирает время по индивидуальному графику сотрудника | `calendar_for_admin` |

**Важно:** расписания этих модулей не объединяются автоматически. Изменение индивидуального графика администратора не изменяет фиксированные часы в `booking/slots.py`. Если в будущем потребуется единое расписание, его интеграцию необходимо спроектировать отдельно.

## API: адреса, методы и права доступа

Аутентификация — JWT. Токен выдаётся по `POST /api/auth/token/`
и передаётся в заголовке `Authorization: Bearer <access>`.

Обозначения прав доступа:

- **Все** — авторизация не нужна.
- **Вход** — нужен токен (любой авторизованный пользователь).
- **Студент** — токен и профиль студента (создаётся при регистрации).
- **Сотрудник** — токен и флаг `is_staff`.

### Авторизация и регистрация

| Метод | Адрес | Права | Описание |
|---|---|---|---|
| POST | `/api/auth/token/` | Все | Получить пару токенов (`access`, `refresh`) |
| POST | `/api/auth/token/refresh/` | Все | Обновить `access` по `refresh` |
| POST | `/api/register/` | Все | Регистрация студента и учётной записи |

### Электронная очередь

| Метод | Адрес | Права | Описание |
|---|---|---|---|
| POST | `/api/queue/join/` | Студент | Встать в очередь своего направления |
| GET | `/api/queue/` | Все | Публичная очередь на сегодня (`?direction=`) |
| POST | `/api/queue/call-next/?direction=` | Сотрудник | Вызвать следующего |
| PATCH | `/api/queue/<id>/` | Сотрудник | Изменить статус талона (`done`, `cancelled`) |
| GET | `/api/queue/reception-screen/?direction=` | Сотрудник | Экран приёма: текущий, следующий, история |

### Вопросы и обращения

| Метод | Адрес | Права | Описание |

| GET | `/api/questions/categories/` | Все | Категории вопросов |
| GET | `/api/questions/levels/` | Все | Уровни вопросов |
| GET | `/api/questions/appeals/` | Вход | Свои обращения (сотрудник видит все), с пагинацией |

| PATCH | `/api/questions/appeals/<id>/status/` | Сотрудник | Сменить статус обращения |

### Общая запись по вопросам — `booking`

### Пагинация

Списки обращений (`/api/questions/appeals/`) и записей к сотруднику
(`/api/calendar/appointments/`) выводятся по страницам.

- По умолчанию 20 элементов на странице, максимум 100.
- Параметры: `?page=2`, `?page_size=10`.
- Формат ответа:

```json
{
  "count": 45,
  "next": "http://127.0.0.1:8000/api/questions/appeals/?page=2",
  "previous": null,
  "results": []
}
```

Остальные списки (вопросы, категории, очередь, правила расписания)
возвращаются обычным массивом.

## Запуск через Docker

```bash
cp .env.example .env      # Windows (PowerShell): copy .env.example .env
```

В `.env` задайте `DJANGO_SECRET_KEY` и `DB_PASSWORD`, `DB_HOST=db` не меняйте.
Если для проекта выданы другие порты, измените `WEB_PORT` и `DB_HOST_PORT`
(по умолчанию 8000 и 5432). Затем:

```bash
docker compose up --build
```

Миграции применяются автоматически. Документация API:
`http://127.0.0.1:<WEB_PORT>/api/docs/`. Запуск тестов:

```bash
docker compose exec web python manage.py test
```

Проекту нужна PostgreSQL: защита от пересекающихся записей использует
ограничения `EXCLUDE USING gist`, которых нет в SQLite.
